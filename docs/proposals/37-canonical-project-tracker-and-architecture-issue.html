37 · accepted · Canonical project tracker and architecture issue synchronization

Proposal 37 · accepted 2026-10-03. One committed Docs ledger set produces one public tracker and one one-way architecture issue per proposal.

The ask

“Update Common Rules to support a single canonical project tracker with architecture-group GitHub issue synchronization.” Aashish · 2026-10-03 · Proposal 37 ledger A-01

What was found

  • Docs already owns 27 ledgers, 59 features and 362 lifecycle rows under the requested canonical directory.
  • Current Common Rules setup discovers only conventional tracker paths, and its one-way issue sync creates one issue per row through gh.
  • The integrated GitHub plugin is installed. Issue #2 already represents Proposal 08, and concurrent Docs work is creating the remaining group issues.
  • The existing board offers delivery layouts, but not the five requested information views or an embedded repository-coherence section.

Options

A · Canonical ledger-to-plugin plan

Common Rules discovers the configured ledgers, generates one validated issue plan, uses the GitHub plugin for mutations and renders architecture, repositories and evidence into the same tracker.

B · Keep separate generators

Docs keeps a custom issue script and the website keeps a separate tracker. Faster initially, but duplicates authority and cannot enforce one reusable Common Rules contract.

Recommended: A, because it keeps one ledger authority while cleanly separating deterministic generation from account-bound GitHub mutations.

Decision at a glance

TAKE One canonical tracker, one group issue per proposal, and no reverse synchronization.

Decisions

Each numbered line is one thing the sponsor answers. Keep the numbers stable once shown: answers and ledger items cite them.

  1. D1. Make the configured Docs ledger directory the sole canonical tracker source.
  2. D2. Add optional proposal-level, ledger-to-GitHub synchronization settings without changing existing projects.
  3. D3. Generate and validate all issue drafts before the GitHub plugin mutates issues; preserve issue #2 for Proposal 08.
  4. D4. Keep GitHub one-way: manual checkbox changes create drift, not ledger writes.
  5. D5. Put architecture, repository coherence and evidence drill-downs inside the canonical tracker.
  6. D6. Validate against Docs read-only, then publish a new Common Rules plugin release.

Decided

Accepted 2026-10-03. The sponsor directed: “Make a goal, implement the common rules and release a new version of the plugin.”

D1–D6 are accepted. The supplied Docs manifest is the target calibration. Two-way synchronization, copied member ledgers and a second public tracker remain explicitly out of scope.
