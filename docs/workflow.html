any sessionrulecheck

Confirm the session is on the current rules

Before reading code, before the worktree, before anything. The rules move several times a day; a session working from what it read this morning is following a version that no longer exists. It prints what changed, not merely that something did. Exit 0 means verified aligned, exit 1 means verified and stale, and exit 2 means it could not check at all — run inside common-rules itself, or a project that never opted in. 2 is its own status precisely so a caller can't mistake "nothing was checked" for "checked, and fine".

project managerL1 · proposal

One proposal per topic — artifact, then buttons

However many agents ran, the topic produces one proposal; each role contributes a section. It arrives as a rendered HTML artifact with a committed copy already in docs/proposals/, and the decision question follows in the same breath, with buttons. One decision per prompt.

It leads with its number. Numbered sequentially per project and never reused; the visible heading and the <title> both read NN · status · Title, so where a thing sits in the sequence and whether it has been decided are legible before a word is read. Status lives in <meta name="proposal-status">: proposed · accepted · completed · completed in part · amends NN · superseded by NN (built is a grandfathered synonym for completed).

A proposal that asked numbered decisions must record the answers — a decision date says when, never what, and proposal-auditor has nothing to measure a build against without them. Scoped mechanically: an <ol class="decisions"> list that asked something needs an id="decided" block answering it before the proposal is accepted; completed in part needs an id="exceptions" block naming what was skipped and why. bin/proposalcheck enforces both, grandfathered by decision date so nothing decided before the rule existed is failed retroactively — and bin/land refuses to land a project whose proposals fail it, the same way it refuses a stale one (LAND_ALLOW_UNRECORDED_DECISIONS=1 to override, recorded either way).

A document is either a proposal or a supporting section — not both, and the difference is whether it carries a status. A lead (no proposal-part-of) is the one thing in its topic asking for a decision, and must carry a proposal-status from the vocabulary above. A section (part-of some lead — an exploration, a findings run, several design-explorer concepts shown side by side before a direction is picked) carries no status of its own, because there is only ever one decision per topic. bin/proposalcheck checks both directions, its own separate floor date so nothing existing is failed retroactively.

proposal-auditorindependent

How far has this moved from what you accepted?

Read-only, decides nothing. Classifies every divergence — faithful, elaboration, drift, silent decision, gap — so the next decision runs on evidence rather than on the project manager's own opinion of its own pipeline.

project managerL2 · approve

Requirements and design accepted, together

Nothing reaches the code engineer before this. Four things escalate past L2 to you and none are judgment calls: it contradicts what the proposal decided, scope moved, a decision surfaced the proposal never made, or it is materially larger than implied.

no L2, no code
code-engineerbuild

Implementation, inside the worktree

UI separated from logic — MVVM for SwiftUI, a services layer for Python/NiceGUI. Commits before reporting. Never certifies its own work, never expands scope, and never starts from a proposal alone.

Briefs go out in one message, never one per turn (proposal 31, O-07 — mandatory). 72% of a project's spend went to lead orchestration against 25% to implementing, because a lead that dispatches one brief per turn pays a full turn — about 134,000 cache-read tokens — for each one. Every unblocked brief in one message; branches reviewed in one pass; six things to say to six agents said once.

pinned to sonnetCHANGELOG entryone message, every brief
test-engineervalidate

Against the criteria, not against the code

Raises structured bug reports; never fixes anything itself. The two negotiate through bounded rounds — a dispute unresolved after two comes to you.

A gate runs in the foreground, one blocking call, and its verdict line is read in the same turn (proposal 31, O-03 — mandatory). Never backgrounded and polled, and a turn never ends parked on a timer: one agent turn costs about 134,000 cache-read context tokens to produce a few hundred written ones, so cost follows the number of turns, not the work inside them, and a poll that finds nothing new re-sends the whole context to learn nothing. "One call" means scoping the run to fit — tools/affected_tests.py before the full suite, not after. If the harness backgrounds the call anyway, its output is read once, on notification, and acted on in that turn. A run too slow to sit through is a bug in the gate, not a licence to poll.

bug reports2 rounds, then escalatenever poll a gate
quality-managerthe gate · risky work

Pre-merge, report-only — for risky work

Runs only when tracker route says restricted or elevated/high-value work; everything else goes build → gate → land with no reviewer. Cheap preconditions first (commit state, merge-base), then outcome-not-surface verification. Fixes nothing, approves nothing — its verdict is a recommendation. Behaviour changed means re-gate; a docstring or changelog line does not.

1 compatible with main2 tests pass3 built & exercised4 changelog
youmerge

Merge, then the clean copy is refreshed

Approving the merge is yours. The task is not finished at the merge: rebuild from main, replace the installed copy, restart it, register it as stable. A merge that leaves the installed app on last week's build has finished the git work only.

A project may declare a staging branch (proposal 31, O-08 — mandatory where declared). Reviewed branches land on staging, the full suite runs there rather than on main, and main only ever fast-forwards from a green staging — so main is provably green at all times. What that reduces is the number of runs, never the coverage. Undeclared, a project behaves exactly as before: straight to main.

The project manager is deliberately not on this list. There is no project-manager.md — a subagent cannot talk to you, and deciding what reaches you is the role's central job, so it sits in the conversation. Invoked with the Agent tool and subagent_type; the behavioural test is blunt — if the session itself is calling Edit, it is no longer the project manager.

How much ceremonylight is the default
FeatureFull pipeline, every role the task calls for.
Small fixCode engineer + quality manager only.
Research / proposalResearch and/or requirements. Nothing merges, so nothing to gate.

Phase sets the default tier — prototype defaults to light, production to full — and phase is a property of the surface being changed, not the whole project. Published research found full-ceremony role pipelines reduced correctness for most models, which is why the tiers exist at all. code-engineer is pinned to sonnet; a separate reviewer catches more of a weaker writer's mistakes than a stronger one's, and that is what makes the pin safe. Never downgrade test-engineer or quality-manager — they are the mechanism the whole trade-off depends on.

Both exist for the same reason: a rule that depends on a session remembering is a rule that decays. Neither is complete — nothing forces a session to call apprun start in the first place, and an unregistered instance is invisible to every later cleanup. That is the honest remaining gap in both.

The short listif you remember nothing else
  • No direct-to-main, ever, and no two chats sharing a checkout.
  • A project that has aligned before must stay aligned to land. bin/land refuses a stale project — not one that never opted in — with the fix commands named.
  • A proposal that asked decisions and recorded none doesn't land either. bin/land refuses via bin/proposalcheck, same opt-in guard, LAND_ALLOW_UNRECORDED_DECISIONS=1 to override.
  • An accepted proposal is not settled requirements. Requirements, then design, then L2 — never straight to code.
  • One proposal per topic, however many agents ran, and it survives across sessions until decided.
  • Show, don't summarise. Artifact over prose; demo before approval; the render, not a description of it.
  • Stop only what you started — and stop the window too.
  • Look before you start, and commit before you pause — uncommitted work is invisible to everyone, including the next check.
  • A question to the user is a cost. If the answer wouldn't change what he sees at a look and isn't reserved, the AI decides, records one line, and proceeds. Unnecessary questions are counted at the gate.
  • You own features; the AI owns the issues they decompose into — cut vertically, never backend-for-X plus UI-for-X.
  • Every project keeps a feature register — a ## Features table in its CLAUDE-checklist.md, one row per feature, linking the issue that is the feature. The Tower reads it: that table is the only answer to what a product is made of and how much is done. It changes when you add, rename or close a feature — never per task. A project without one reports "no features declared", never 0%. States: in flight · next · blocked by #N · later/version N · built · completed (done is a grandfathered synonym, same convention as proposal-status's own built → completed).
  • And every project keeps a milestone plan — a ## Milestones table beside the register, sharing its states, with two columns the register has no equivalent of: Proves and You get. The register says what the product is made of; this says what order, what each step establishes, and when the sponsor gets something he can hold. A milestone ends in something proven, not delivered — "the index builds" is a task, "retrieval is good enough to build on" is a milestone. The result that would stop the plan is written before the work starts; written after, it is a rationalisation of whatever the data said. And every row states what the sponsor gets including when the answer is nothing — a plan whose first four steps hand him nothing is fine, but he should be told at the start rather than find out in week three.
  • Parallel work gets lanes — an optional Track column names a workstream per row, for a project running more than one thread at once (finance-tracker moves correctness and surfaces together). The picture draws one lane per track instead of one rule, in the order the plan first mentions them, each lane carrying its own here: with parallel work there is no single front, and collapsing them to one would assert an ordering between lanes the plan never claimed. Omit the column and nothing changes — a single-threaded project should not pay for the concept.
  • The plan has a picture, and it is generated — bin/milestones renders docs/milestones.html from the table: lanes, states, and a marker wherever something reaches the sponsor's hands. bin/land refuses a project whose page is missing or stale, on the same opt-in guard as the other gates. Generated, never written — a hand-maintained second copy of the plan is the drift this rule already warns about with extra steps, and the picture is the copy people look at. Staleness is checkable because the page carries a digest of the plan's content, so the question is "does this still show the plan" rather than a byte comparison a timestamp would defeat.
  • The milestone plan is live — kept current until the feature is done, because a plan that is not maintained asserts an order of work that has stopped being true. Three things move it: a state changes, a proof lands (recording what actually happened when it differs from the prediction), or a proof forces a reorder. Still never per task. The test: a session editing because it did something is writing a logbook and is wrong; editing because something is now known is maintaining the plan and is right.
  • The warm-up standard is mandatory. Every project under apps/ follows proposals 19–21 — one ledger shape, one card, one proposal shape. /warmup opens every session and runs again after a compaction; the sponsor's /standard is what adopts it for a project. A CHANGELOG.md entry here beginning Standard change (mandatory) is implemented before the next rulecheck --align — never the reverse.
  • One tracker per project (proposal 29). A single page, docs/proposals/tracker/index.html, covers every ledger, published at one stable URL — until the sponsor asks for another tracker, recorded in that ledger's tracker key.
  • Token budget (proposal 23). A lead ends at a milestone, at the end of a day or past about 150k tokens of context, and hands over through the ledger, tracker checkpoint and /warmup. Small issues on one surface are one bundle: one agent, one commit per issue, one gate, one PR. A read-only Haiku scout writes the builder's CONTEXT pack (templates/scout-brief.md). Gates run through bin/quiet; ledger changes go through tracker set and tracker ask; files are read with the Read tool, not cat or sed -n.
  • Nothing about features, merges, promotions or these rules happens without you.
How this page stays true

It is derived from CLAUDE-workflow.md, not a second source of truth. Where they disagree, that file wins and this one is wrong.
